# Access control

Browser-local roles are synthetic demo identities and protect no shared data. Never put real personal or sensitive unpublished data in this mode.

All shared tables enable RLS. Public clients can read published entries, articles and releases. Authenticated contributors can create drafts, read their own revisions and submit them through a function. Assigned reviewers and editors can read authorized proposals. Independent editors authorize publication and dispute resolution. Technical admins can read operational audit logs and profiles but cannot editorially transition proposals.

Published tables, review decisions, role assignments and audit logs have no direct client mutation policies. Workflow functions check identity, ownership, role, current status and nonempty rationale; review operations lock the revision row. Audit triggers preserve before/after proposal content. Exports omit unpublished revisions.

Use only the publishable key on server requests with user cookies. Keep service-role keys outside the application. API mutations require a same-origin request, valid session and schema-valid input. Profile/comment authors are always taken from `getUser()`, never browser input. Email sign-in permits new users only when project signups are enabled; it never grants editorial roles. New users save their own display-name profile and can contribute under the existing own-draft policies. Next Proxy refreshes cookie sessions using verified claims; every protected handler independently calls `getUser()`. There are no automatic account creations or test email sends during verification.

Set `APP_ORIGIN` to the canonical HTTPS origin in production. Local request-origin handling accommodates Next's localhost normalization only for loopback hosts with the same port; unrelated hosts and origins remain rejected. With explicit user approval, the project's allowlist now contains the exact local callback `http://127.0.0.1:3000/auth`. No wildcard redirects or weaker auth settings were added. Session responses are private/no-store. Shared profile/submission content is not persisted to local storage. Unavailable community workflows do not fall back to demo roles or data. Before shared use, finish real email/session tests, role/article/release enforcement, rate limiting, RLS integration tests, backup procedures and security review.

Local follow-on controls deny self-elevation and self-review, separate editorial and operational grants, enforce reviewer assignment, preserve article/release snapshots and validate saved state. Invalid saves are retained under a recovery key. Submitted text is escaped by React. Headers deny framing, object embedding, MIME sniffing and device permissions. The policy intentionally stops short of a nonce-based script CSP; add that with authenticated server integration. Browser-local permissions are demonstration behavior, not a security boundary.

Both migrations are executed by `pnpm test:db` in embedded PostgreSQL (PGlite), with mocked Supabase `auth.uid()` and synthetic users. Tests cover private drafts, immutable snapshots, role escalation denial, administrator restrictions, independent reviews, publication, preserved corrections, disputes and license gates. The same migrations were applied through the project's SQL Editor and verified: 13 RLS-enabled tables, nine workflow functions, two audit triggers and successful anonymous PostgREST reads. Authenticated hosted RLS and session-revocation tests remain pending. Docker's daemon is unavailable for a separate local Supabase stack.
